# Qualify watching, recovery and automatic cleanup together

The idle-maintenance measurements disable watching and later recovery. Exercise the
combined native host configuration before changing source-backing or scheduling defaults.
This is qualification work, not a production scheduling change unless a defect is found.

## Workloads and evidence

Run real native watching, two-second periodic recovery and idle maintenance over marked
owned pinned Linux/PyTorch copies. Abort if native watches are unavailable; never silently
label polling fallback as watcher qualification. Source writes and restoration use no
explicit host hints in this mode.

Retain the three alternating pairs around automatically admitted generated-tail cleanup.
Watching/recovery are enabled, but record their actual status before/after each write.
Admission deliberately waits for recovery, so do not claim simultaneous three-way overlap.
Add three writes immediately after recovery is observed running. Status sampling shows
observed activity, not exact parser/capture overlap; recovery can finish after the sample.

Record write-to-correct-settled observation, watcher mode, recovery counters/measurements,
maintenance counters and real cut intervals. Do not associate an unlabelled per-file
capture trace with foreground work while recovery can also capture. Keep raw diagnostics
and distinguish scoped/reconciled latest operations without claiming exact attribution.
Periodic recovery can discover an edit as well as native events; this qualifies the
combined configuration rather than isolating notification delivery latency.

Verify each changed source, expected declaration, fresh facts and retained old pin.
Restore original source/identity between writes and compare final complete clean capture.
No analysed project tooling or original archive writes. Preserve hashes, source counts,
actual/missed cleanup overlap and recovery observations. Setups/verification are untimed
but contribute to peaks; child address-space limits do not qualify physical RAM.

## Verification and limits

Use TDD for configuration, native watcher requirement, watcher-only publication/restoration,
recovery-observed writes and diagnostics. Run workspace/doctest/fmt/Clippy/browser checks
and appropriate mutation scopes for any new qualification validation or production change.
Benchmark release builds separately from correctness/cache preparation jobs.

Use three samples per condition/profile. Warm finite native results do not establish
browser latency tails, cold storage, other platforms, full-capacity pressure, blocked
shutdown or baseline-laptop qualification. Scheduling/storage defaults remain unchanged.

## Delivery evidence

The [qualification report](../../experiments/interactive-maintenance/RESULTS.md) records
the completed runs and their limits. Production scheduler/storage code is unchanged.
The recovery-observed samples form a three-write burst within one pass per repository,
so they do not establish independent recovery-cycle distributions.
