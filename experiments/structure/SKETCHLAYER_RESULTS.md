# Reserved Sketchlayer structural trial

For maintainers deciding whether to invest further in natural-language navigation.
**The prototype provides useful explicit inventories/call-site navigation, but this trial
does not establish a clear advantage over ordinary text search or justify a model layer.**
The source-informed replay reaches the right implementation points and retains actual
invocation text. Source reading and framework knowledge still supply the answers.

The [source reference](SKETCHLAYER_SOURCE_REFERENCE.md) explains where a new tool belongs
and where an active-canvas border could be introduced. It was assembled after first
outputs and includes official GTK documentation for the activity/CSS distinction. It is
not an answer generated by this prototype, and no Sketchlayer feature was implemented.

## Frozen candidate and unseen protocol

Candidate commit `6c4bce2` and [binary/source hashes](candidate.json) were frozen after
independent development checks and before exporting/inspecting Sketchlayer. The
[reservation](../companion/library/sketchlayer.json) preserved the maintainer's questions
and revision `f52314e676ead6a50913e89a458ec34c23d509f9`. Only directory/revision/status had
been inspected before freezing; no source or retrieval was used for development.

1. “Where do i go to add a new tool?”
2. “how would I add a border around the main drawing surface to make it easier to tell
   when it's the top window?”

The [literal-seed plan](sketchlayer-plan.json) was recorded after the candidate freeze and
before source inspection: `tool` for question 1; `border`, `surface`, `window` for question 2.
These are evaluator-selected words from the questions, not automatic natural-language
interpretation. Structural area/inventory operations and ordinary `rg` received the same
seeds. Original/focused question-search controls received untouched full questions in a
counterbalanced order. No query, seed, ranking, model or production code changed afterwards.

The immutable export contains 20 regular files, including nine Rust files. All nine were
indexed/admitted with zero additional projection/search omissions. Source acquisition did
not build or execute the inspected project. Framework/dependency implementations remain
outside this corpus. All first responses/text outputs were saved and hashed before source
reading or source-informed navigation. These cases are now observed evaluation cases.
The older eight reserved real-source cases remain unrun.

## First observations

| Input | Structural declaration/area results | Equal-seed text search |
| --- | --- | --- |
| `tool` | Three matching areas, 13 declarations; includes `Tool` and `DrawingState::set_tool`, plus toolbar declarations. | 127 matching lines, including enum variants, drawing branches and toolbar wiring. |
| `border` | No area/declaration matches. | One line: selected-toolbar-button CSS, not the canvas surface. |
| `surface` | Two areas/declarations: image-cache/export helpers. | 19 lines, mostly image-surface operations. |
| `window` | Four areas, 22 declarations; includes `CanvasWindow` and its implementations. | 91 lines across canvas/tool-window/window abstractions and startup. |

Counts describe different amounts of information, not quality or human-effort scores.
The structural `tool` inventory makes the relevant enum/setter explicit. Text search also
contains those locations and provides non-call references that this prototype lacks.
For the border question, neither the noun `surface` nor an existing border hit identifies
the right canvas behaviour automatically; selecting the canvas from window-related
results still requires interpretation.

Unchanged question-search controls remain limited. Original matching for the tool question
repeatedly selects toolbar-constructor fragments; focused matching offers the startup,
toolbar and a drawing-file fragment. For the border question, focused matching selects
registration/example-like startup/drawing fragments, while original matching reaches
`CanvasWindow::new` at rank 5. No control automatically supplies the active-window/CSS
implementation decision. Low request latency does not establish relevance or completeness.

## Source-informed navigation and retained context

After the first observations, the evaluator read source and replayed two workflows:

- Tool: choose the drawing-file inventory, inspect `set_tool`'s candidate uses, and reach
  the toolbar closure at `src/tool_window.rs:163`. The kept six-line window includes the
  actual `set_tool(tool)` call. `Tool` itself has zero same-name calls even though its enum
  variants are used throughout the app; type/variant references are outside call extraction.
- Canvas: choose `src/canvas.rs`, explicitly open the full area inventory, follow written
  calls from `CanvasWindow::new` to `setup_drawing`, then inspect the `DrawingState::draw`
  invocation inside the draw callback. The kept window starts at `src/canvas.rs:156` and
  contains the supporting call. A selected trail continues into `DrawingState::draw`.

The replay made four metadata requests for question 1 and eight for question 2, including
initial area loading, filters/pages and selected steps. Those are source-aware automated
operations, not independent human navigation costs or an end-to-end time comparison.
No attempt was made to handicap an editor user who could choose more precise search terms
or already knows GTK conventions. With only nine Rust files, ordinary search remains a
competitive baseline; a clear human advantage has not been demonstrated.

Both questions were saved in separate investigations, with no page errors. Working-source
handoffs used recording editor scripts. No real editor window or target app was launched,
and owned hosts/browser instances stopped. Both retained windows include their chosen
invocation; this improves the source-informed replay's retained support versus keeping
unrelated declaration headers, without fixing the older generic six-line-range limitation.

## Remaining limitations observed

- Candidate names do not resolve GTK methods, imports, traits, receivers or dynamic dispatch.
  Source ownership of the `draw` callback is not proof that drawing executes synchronously
  during `setup_drawing`.
- Name/path filters do not include enclosing qualification in every match: the `window`
  filter finds `CanvasWindow` but can hide its short-named `new` method. The evaluator used
  **Area inventory** to remove the filter; no candidate change was made to repair the case.
- Type/variant uses are absent. Zero calls to `Tool` cannot support an unused-code claim.
- Following a new target can retain the panel's prior scroll position, hiding the trail/header
  until the reader scrolls back. This was observed and left unchanged during evaluation.
- The activity requirement is ambiguous: canvas focus, either app window active, and stacking
  are different. The source makes the toolbar transient for the canvas. Structural results
  cannot invent that product decision or external GTK state semantics.

## Optimized metadata cost check

After tests/mutations stopped, a separate known-development-repository run indexed 208
Vizzi Rust/Python files with one worker at nice 10. This was not held-out relevance testing.
Thirty warm full-body localhost observations after five warmups gave:

| Operation | Median | p95 |
| --- | --- | --- |
| Areas/name lookup | 0.93 ms | 1.13 ms |
| One-file declaration inventory | 0.94 ms | 1.54 ms |
| Written calls page | 0.66 ms | 3.94 ms |
| Same-name uses page | 0.79 ms | 1.47 ms |

Source activation took 833 ms; cold metadata projection/query took 26 ms. The projection
reported 217 omitted call sites under the spelling/count allowances and zero omitted
files/declarations/areas. The longest response was about 25 KiB. Observed process-tree PSS
peaked at 0.194 GiB, including the native host/Node driver and excluding a browser/editor/model.
Memory sampling was observational at 250 ms, not an enforced cap. This is metadata cost
on a known development workload, not human task time, physical frame time, large-repository
qualification or evidence that a model would be free.

## Verification, artifacts and consequence

The frozen development checkpoint passes 533 workspace tests/doctests, formatting, Clippy,
the full browser suite and 20 QA helper files. Its mutation categories and limitations are
recorded in [development results](DEVELOPMENT_RESULTS.md). No production change followed
unseen source inspection. All cohort/candidate/first-output/source hashes were checked,
and the real-source replay verified previews, separate saved questions, invocation content
and recording-only arguments. Experiment drivers were syntax-checked/executed; the Rust
baseline is the frozen candidate evidence, not claimed as rerun after documentation.

Keep the structural view experimental and stop expanding the hand-tuned natural-language
layer. A small model's routing/selection value remains untested; no new training, weight
editing or model deployment is justified by this run. The useful next acceptance activity
is an actual maintainer trying the two explicit views beside an editor and reporting
whether they improve understanding/retention. Successful syntax extraction and scripted
navigation alone do not clear that gate.
